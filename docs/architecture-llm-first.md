# 分层裁判：LLM 决策，路径保证可靠（架构约束）

> 状态：已落地（路由骨架）· 2026-08-18
> 消费者：任何涉及路由/意图判定/新工具的改动，动手前必读。本文是**反方意见 + 架构约束**，不是建议。
> 取代：早期「全删正则、LLM 唯一裁判」的激进方案（仅对话讨论，从未落盘）。

## 一句话

**正则不是敌人，是不该出现在写路径上的裁判。** 拆的是「正则在写路径上抢答」，不是「正则存在」。

## 原则：分层裁判

| 层 | 请求 | 裁判 | 依据 |
|---|---|---|---|
| 斜杠命令 | `/对账` 等（用户显式选择） | 确定性直接派路径 | 用户已拍板，无歧义 |
| 读/低代价操作 | 提取选中列、拍平表头 | **轻量正则保留** | P(错)≈0、代价≈0，不需要 LLM |
| 写/流程类 | 对账、整形、规整、计算、业财 | **LLM 唯一裁判** → `run_flow` | P(错) 有地板，代价高，必须语义理解 + 提交门 |

**分工依据是期望损失不等式，不是"谁更纯粹"：**
- 读操作：正则抢答的期望损失（≈0）< LLM 先行的成本（延迟+token）→ 留正则
- 写操作：正则抢答的期望损失（歧义×高代价）> LLM 先行（提交门可消化）→ LLM 判

## 已落地（2026-08-18）

- `run_flow` 工具（`addin/skills/core/flows/manifest.json`）：LLM 选流程，流程内部按固定步骤执行（inspect→ensure→算子→新表），源表不覆盖。流程：reconcile / extract / project / flatten_header / reshape / calculate / finance。
- 拆掉写路径预抢答：`isReconcileRequest` / `isReshapeRequest` / `isProjectReshapeRequest` / `isCalculateRequest` / `isFinanceRequest` 不再在 LLM 前路由。
- 保留精确低代价正则：`isExtractRequest`（提取X列/大小写）、`isFlattenHeaderRequest`（拍平表头）。
- 系统提示加「流程执行（run_flow）」引导。

## 已知缺口（必须按顺序补，不能跳过）

1. **B 类歧义前置（已缓解，未消除）**：LLM 选错流程是静默错误。缓解三件套（2026-08-18 落地）：
   - 系统提示「歧义前置」：请求可能对应多流程时，先列候选让用户选，确认后才 run_flow；
   - run_flow 执行前明示选中的流程（`🔧 run_flow(flow=…)`），让选错可见；
   - 流程写新表、源表不覆盖（低代价兜底）。
   **诚实边界**：B 类无法完全结构消除（任何解释都"合法"，只有用户知道要哪种）。缓解依赖 LLM 识别自身歧义 + 用户一次选择，可能漏判或误确认——所以「写操作提交门」（缺口 2）仍是必要补强。
2. **写操作提交门**：高代价写动作（覆盖、格式转换）应「提议 → 人确认 → 执行」。当前 run_flow 执行后写新表，源表不覆盖，是部分保护；覆盖源表的路径必须有确认。
3. **确认衰减**：提交门/歧义前置的可靠性随使用次数衰减（自动化自满）。对策：每门注意力成本最小化（一个干净 diff + 一个决策点）+ 确认预算上限。

## 禁止

- 重新把写路径预抢答放回客户端正则（reconcile/reshape/project/calculate/finance）。
- 新增写算子不进决策表直接上路由。
- 用"架构更纯粹"当理由绕过期望损失不等式。
