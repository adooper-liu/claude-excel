## 一、跨境电商的资金到底怎么流的

一个中国卖家在美国站卖出一件 $29.99 的商品，钱要经过四层才能回到口袋（数字为**教学示例**，非实证统计 — C）：

```
第 0 天    卖家向供应商付款（采购 + 头程物流）          -$8.00 现金流出
第 15 天   货上船 / 入 FBA 仓                          库存占用
第 45 天   买家下单 $29.99                              订单产生
           ├── 亚马逊扣平台费（佣金 15% + FBA + 燃油 + 仓储）  -$8.12
           ├── 广告费（TACOS 6%）                          -$1.80
           ├── 退款预估（3% 退款率 × 售价）                 -$0.90
           = 亚马逊应结算                                    $19.17
第 60 天   亚马逊每两周结算一次，打入收款工具虚拟账户
           ├── 收款工具手续费（连连 0.25% / PingPong ≤1%）   -$0.05~$0.19
           = 收款工具到账                                    $18.98~$19.12
第 62 天   卖家从收款工具提现到国内银行
           ├── 提现手续费 + 汇率差价                         -$0.10~$0.30
           = 国内银行到账                                    ~$18.68~$19.02
第 80 天   减去其他（汇兑、索赔、杂费）                     -$0.60
           = 净回款                                          ~$18.08~$18.42

净利润 = 净回款 $18.08~$18.42 - 采购成本 $8.00 = $10.08~$10.42（约 33.6%~34.8%）
```

> **验算**（C，教学示例）：平台费 $4.50+$3.45+$0.12+$0.05=$8.12；亚马逊结算 $29.99-$8.12-$1.80-$0.90=$19.17；
> 净回款下限 $19.17-$0.19-$0.30-$0.60=$18.08；上限 $19.17-$0.05-$0.10-$0.60=$18.42。净利润 $10.08~$10.42。
>
> **广告扣费新规（修正版）**：2025-08-01 起，**仅收到平台定向通知的卖家**，广告费改为**优先从店铺回款余额实时划扣**，
> 信用卡降为备用扣款方式（余额不足才触发），并**可申请发票月结（30 天账期）**保留资金缓冲。
> 原表述「预付实时扣、余额不足立即暂停」不准确：不是预付充值制，也不是立即暂停（B，见附录 S5）。

这笔账的关键不是"某一单赚了多少"，而是**时间差**：采购付款在第 0 天，回款在第 62-80 天。
中间 60-80 天里，钱压在库存里。一个卖 100 个 SKU 的卖家，账上可能有 30-50 万压在 FBA 仓 + 在途货 + 国内备货里。
利润算得再准，现金流转不过来就是"赚了利润、死了现金流"。

## 二、真实痛点排序

根据从业者讨论与社区数据（方向性判断 — C，排序依据为**决策频率 × 决策金额 × 现有工具缺口**，待真实用户访谈验证）：

**第一痛点：现金流被库存吞噬**

库存资金周转 60-90 天。卖家最焦虑的不是"这个 SKU 利润算得准不准"，而是"账上赚了 50 万，但钱全在货里"。
补货要垫资，回款有账期，中间任何环节卡住就是资金链断裂。

**第二痛点：多源数据拼接困难**

亚马逊结算报告有订单级明细，Advertised Product Report 有 SKU+日期级广告花费——数据本身是有的。
但它们分散在不同报告里，格式不同、粒度不同、下载周期不同。卖家需要手动拼接才能回答
"这个 SKU 到底赚不赚钱"。大促期间数据量暴增，Excel 拼接极易出错。

**第三痛点：利润核算失真**

银行收到一笔钱，里面混着平台费、广告费、退款、汇率波动——如果不逐项拆分，很容易"看着赚钱、实际亏钱"。
常见失真来源包括：错把到账当营收、费用未按 SKU 分摊、存货核算缺失、遗漏平台扣款（B，第三方媒体转述，见附录 S6）。

**第四痛点：广告归因的时间偏移**

SP 广告归因窗口 7 天，SB/SD 是 14 天（A，亚马逊官方口径 + 行业多源一致）。
广告点击日和订单成交日不在同一天，按不同口径对账结果不同。

## 三、Gate 1b 做了什么

定位：解决**第三和第四痛点**——利润核算与广告归因。已落地能力（与当前代码逐条核对过）：

| 环节 | 做了什么 | 落点 |
|---|---|---|
| 数据进簿 | CSV/fixture → canonical 列映射（SKU、日期、金额归一） | `connector_load_feed` + `write_to_sheet` |
| 订单×广告对账 | `date_window` 匹配（±7 天归因偏移），配对行标 `__review` | `reconcile_tables` |
| 利润假设 | 参数区 9 个输入格（B2–B10：汇率/佣金率/退款率/FBA/仓储/支付手续费…），黄底=可改 | `write_inputs` |
| 活公式计算 | 按 SKU 的 SUMIFS 收入骨架 + `write_formula` 补减项列，**全部引用参数单元格**，改参数→净利联动 | `calculate_table` + `write_formula` |
| 透视分析 | 按 SKU / 日期切片（收入 + 广告花费） | `create_pivot` |
| 审计追踪 | `_pack_audit` 记录：匹配数/冲突数 + **源文件 hash（connector 返回的 sourceHash）** + **假设参数快照** + 匹配率 | `append_pack_audit` |

**架构上值得注意的设计**（这是产品真正的护城河基础）：

- **写格权管控**：Pack 层（Skill + `user.*` 函数）不能直接写 Excel 单元格，只能通过核心算子写。
  这不是"技术优雅"，而是防止 AI 在财务数据上乱写。
- **源表只读**：对账和整形只写新表，不碰源数据。`write_to_sheet` 被禁止写入 reconcile/reshape 命名的 sheet。
- **反幻觉规则**：利润模型文档明确禁止编数字、拿个案当基准、让 LLM 心算利润。知识来源必须标注。
  所有费率只以**区间**呈现（如佣金 8%–15%），单点精确值必须由用户参数区提供。

**Pack 化（2026-08 新落地）— 对外卖点**：

整个场景现在是一个**可装卸的 Pack**：流程编排写在 SKILL.md 里（一份 Markdown 手册，8 步强模板），
费率默认值、公式模板、结论格式都作为文档附录存在。

- **改口径 = 改文档 = 重装 Pack，不用等软件升级、不用重新编译加载项**。
  比如佣金率默认值变了、想加一个减项列——改一行文档，用户侧重新加载即可。
- 这解决了 SaaS 类竞品最常见的痛点：**"我只是想改个计算规则，为什么要等版本发布？"**
- 对卖家意味着：假设参数可以自己改，连"公式怎么算"也可以让服务方改完直接更新，不动 Excel 文件本身。

## 四、Gate 1b 没做什么（诚实清单）

| 缺口 | 说明 | 业务影响 |
|---|---|---|
| **现金流管理** | 不碰库存资金占用、采购付款节奏、回款周期 | 卖家最痛的问题没解决 |
| **收款工具层** | 资金流模型止于"亚马逊结算"，不含 Payoneer/连连等收款工具费 | 利润计算差 0.25%–1% |
| **结算×银行对账** | 做了订单×广告，没做结算报告×银行流水 | 资金侧闭环缺失 |
| **批次成本核算** | COGS 用固定费率假设，不支持 FIFO/加权平均 | 同一 SKU 不同批次采购价不同时算不准 |
| **固定成本分摊** | 只有变动成本（佣金、FBA、广告），没有仓租/人工/ERP 订阅的分摊 | "SKU 净利润"不含共享成本，实际是"边际贡献" |
| **多平台** | 只覆盖亚马逊，不含 TikTok Shop / Walmart / 独立站 | 多平台卖家无法使用 |
| **ERP 数据打通** | 从 CSV 开始，不跟 ERP 对接 | 已用 ERP 的卖家需要重复录入 |

> 诚实是可信度的前提：**没做什么先说出来**，比"什么都做"更能建立信任。
> 这份清单同时定义了 Phase 2/3 的边界——现金流、收款工具、批次成本、多平台，
> 是决定产品能否从"补充工具"变成"必备工具"的关键，但都不是现在。

## 五、与 ERP 的真实关系

一个已经在用领星/积加的卖家，ERP 已经能做：API 自动拉取结算数据、SKU 级利润计算、结算×银行自动对账、封存审计。
**这一点必须承认**：如果卖家需要的是"自动拉数据 + 出利润报表"，ERP 做得更好、更快、更自动化。
Claude Excel 的 CSV 手动导入模式，适合**没有 ERP 的小卖家**或**ERP 数据不够用的补充分析**，不适合替代 ERP。

Claude Excel 相对 ERP 的**三个真实差异点**：

1. **口径透明**：每个数字怎么算出来的，写成可读口径 + 引用单元格的活公式，不是藏在系统黑盒里。
2. **假设可改**：ERP 给"封存后重算"，Claude Excel 给"参数区 + 活公式"——改一个数字全表联动，不走封存流程。
3. **零部署门槛**：不需要 ERP 实施、不需要 API 对接、不需要培训。打开 Excel 就能用，自带审计留痕。

### 主战场：H3 敏感性分析（真正打 ERP 差异化的场景）

ERP 的口径是**死的**——问它"如果退款率从 8% 涨到 12% 会怎样"、"如果汇率从 7.2 跌到 7.0，
哪些 SKU 会从赚钱变亏钱"，它给不了，因为它的利润报表是封存的、口径固定。

而这恰恰是**Excel 的天然主场 + AI 增量最明显**的场景：

- **自然语言改假设**：说"把退款率改成 12%"或"汇率按 7.0 算"，AI 直接改参数区，活公式全表联动重算；
- **批量敏感性**：一次把退款率 8%/10%/12%、汇率 7.2/7.0/6.8 的净利矩阵跑出来，标出临界点 SKU；
- **人话解释**："有 3 个 SKU 在退款率 10% 时转亏，主因是广告占比偏高（TACOS > 15%）"——
  结论有追溯：每个数字都能回到口径表单元格。

用大白话说：**ERP 告诉你"现在是多少"，Claude Excel 帮你回答"如果…会怎样"**。
后者是决策问题，前者只是报表问题。

## 六、一句话重新定位

Gate 1b 不是"财务闭环工具"——它解决的是**跨境电商利润核算中"数据拼接 + 假设分析"这个具体环节**。
它不碰现金流管理、不碰库存、不碰结算对账、不碰 ERP 数据对接。

它的价值不在于"做了多少"，而在于**做的方式**，三件事（都是 ERP 黑盒和原生 Excel 给不了的）：

1. **口径透明**：每个数字怎么算的，AI 写成可读口径 + 引用单元格的活公式；
2. **异常把关**：匹配率 <90% 标红提醒"净利为近似口径"、退款负金额不静默加进汇总、归因偏移写入审计行；
3. **审计留痕**：源文件 hash + 假设参数快照 + 审计行——对完账能给人看"这数怎么来的"。

加上 **Pack 化**（改口径=改文档重装，不发版）与 **H3 敏感性分析**（"如果…会怎样"的决策支持），
组合起来的一句话：

> **在 Excel 里，用大白话把账算清楚、说清楚、改得动、能复核。**

起点不等于闭环。从"利润核算的一个环节"到"业财闭环"，中间还隔着现金流管理、收款工具对接、
批次成本核算、固定成本分摊、多平台支持——这些是 Phase 2/3 的事。
