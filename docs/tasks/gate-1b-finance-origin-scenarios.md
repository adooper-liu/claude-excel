## 0. 结论先行

- **结算单（Settlement Report）是亚马逊 FBA 卖家的现金实现锚点（实收），不是「财务原点」。**
  一笔跨境销售有三个记账时点：**订单 = 应收**（收入发生日）、**结算单 = 实收**（现金到账日）、**广告 = 费用**（营销消耗）。
  「业财闭环」的正确定义是**三账本对齐 + 差异解释**：`订单额 − 平台扣费 − 退款 = 实收`，结算单是**验证器**，不是唯一真相。
- **范式边界**：结算单锚点只对 **Amazon FBA 卖家**严格成立。Temu 全托管/半托管卖家只收供货价、无对 C 端结算单；Shopify 独立站的钱从 Stripe/PayPal 进来，对账对象是**支付服务商对账单 + 银行流水**。本 Pack 场景均以 Amazon FBA 为基准，其他平台另立。
- **当前 Pack 的 `orders + ads` 两个 feed** 覆盖了收入侧的成交日报表与费用侧的广告报表，但结算枢纽、COGS/头程、FBA 明细、退款全成本、汇率/汇损均未进模型。
- **Gate 1b 定位修正：技术验证闭环**（验证写格单通道安全、reconcile 算子质量、`_pack_audit` 审计机制），**不是商业闭环**。商业验证另立 H3（敏感性分析）——它命中「ERP 不做/做不好 + Excel 天然主场 + AI 增量明显」三条件。

## 2. 高纯度需求场景（v1 六场景 → 收敛为 H1/H2/H3）

> 收敛逻辑：场景 5（退款全成本）⊂ H1 的减项 + H2 的费用行，合并；场景 6（多币种）⊂ H2 的多平台变形，合并；
> 场景 4（现金流）依赖结算历史，新用户无数据，**砍掉**（等 3+ 期结算后另立）；场景 3（广告归因）保留为 H1 的验证性子项。
> 排序依据改为「**决策频率 × 决策金额 × 现有工具缺口**」（v1 的「付费意愿排序」无访谈实证，弃用，标注**待真实用户访谈验证**）。

### H1 单 SKU 净利核算（保留，重写卖点）

- **老板的问题**：按 ASIN/SKU 的**真实**净利（不是毛利、不是订单金额），哪个 SKU 在亏钱。
- **真实数据源**：订单（收入）+ 结算单（该 SKU 被扣的真实费用）+ COGS 表（采购 + 头程均摊）+ FBA 费用（配送 + 仓储分摊 + 超龄附加）。
- **口径要点**：`净利 = 订单本币×汇率 − COGS − 佣金 − FBA配送 − 仓储均摊 − 广告(归集) − 支付手续费 − 退款预估`
  （与 `profit_formula.md` §一 一致；**退款全成本**并入：退款金额 + 佣金不退部分(20%，S6) + 退货处理费，不静默加负金额进汇总）。
- **卖点（重写）**：不是「算净利」——Excel 透视 + SUMIFS 也能凑合；而是**口径可调**（每个减项写成可读口径 + 引用单元格的活公式）+ **假设驱动重算**（改 B2–B4 → 结果联动）+ **审计留痕**（假设快照 + `_pack_audit`）。
- **验证性附带项**（原场景 3）：reconcile ±7 天归因偏移已做（只标注不解决）；补 TACOS/ACoS 标注列 + 跨格式归因虚增 8–40% 警示（S8）。
- **产品现状**：公式在文档里定义完整（`profit_formula.md`），**代码只跑了 SUMIFS(item_price)**——只汇总订单金额，没算净利；COGS 映射表、FBA 明细、退款过滤均未接入。

### H2 结算单拆解（保留，定位降级为技术验证 feed）

- **老板的问题**：我这个月销售额 $50,000，银行到账只有 $38,000，中间 $12,000 去哪了？（亚马逊 FBA 卖家的第一问）
- **真实数据源**：Settlement Report（14 天周期，TXT/XML 下载，字段见 S1/S2，以实际导出为准）。
- **口径要点**：按 settlement 逐行把扣费归到 佣金 / FBA 配送 / 仓储 / 广告 / 退款（含管理费 20%）/ 其他（移除、拒付、订阅）六大类；多币种时按结算日统一汇率（原场景 6 并入此处，不独立成景）。
- **定位（v2 降级）**：从「商业闭环」降为**技术验证 feed**——证明「CSV → 对账 → 审计」管道能接住平台结算单这种**结构最复杂的数据源**（逐行混合订单/退款/费用事件）。商业价值不在此处主张。
- **产品现状**：**无此 feed**。现 Pack 用订单金额做收入、广告 spend 做费用，算不出「销售→到账」桥表。

### H3 敏感性/假设分析（**新增主战场，商业验证候选**）

- **老板的问题**：退货率从 8% 涨到 12%、汇率从 7.2 跌到 7.0、佣金从 15% 涨到 17%——净利怎么变？哪些 SKU 到临界点就亏？
- **为什么是主战场**：① **ERP 给不了**——积加/领星/马帮的口径是写死的黑盒；② **Excel 天然主场**——活公式 + 参数单元格 + 条件格式标临界；③ **AI 增量最明显**——自然语言改假设 + 自动生成引用参数的活公式 + 解释「这个 SKU 为什么到 12% 就亏」。
- **产出形态**：参数表（汇率/退货率/佣金率/FBA 费率…）+ 净利活公式（全部引用参数单元格）+ 临界点标色（净利≤0 的 SKU 显红）+ 一句话结论（AI 解释驱动因子）。
- **依赖**：H1 的净利公式先落地（活公式是敏感性分析的前提）；G5 把关（阈值标色）是其交互基础。

## 6. 与现有 Gate 1b 的关系

- 现有验收（2026-08-16「订单×广告 → 利润假设」30 分钟跑通）**不废**：它验证了「CSV → 对账 → 透视 → 审计」的管道能力。
- 本方案是**场景定位修正**：Gate 1b 的本职是**技术验证闭环**（写格单通道安全、reconcile 质量、`_pack_audit` 审计机制），
  价值是**内部研发验证**，不是**外部商业卖点**——业财对账/利润核算正是积加/领星/马帮的拳头功能且数据源在它们手里（API 自动同步 vs 我们手动导 CSV），正面打没有赢面。
- **商业验证另立 H3**（敏感性分析）：命中「ERP 不做/做不好 + Excel 天然主场 + AI 增量明显」三条件。
- 验收口径建议改为：**用 1 份真实结算单（可脱敏）+ 1 份订单 + 1 份广告，跑出「销售→到账桥表 + 单 SKU 净利（假设驱动）」**，才算技术闭环。

## 7. 信源分级纪律（v2 新增，写进后续所有 brief）

1. **三级标注**：A = 官方原文或 ≥3 独立来源一致；B = 第三方转述/聚合，或官方页未开原文；C = 方向性/示例，数字不可引用。
2. **C 级数字一律降级或删除**——宁可无数字，不引无实证数字。
3. **引用第三方数字必须回原文核对语义**——比「无来源」更危险的是「有来源但内容被改写」（v1 S9 的教训）。
4. **标注「官方」必须有开过原文的实证**——卖家后台/帮助页需登录的，如实标「未开原文，以实际导出为准」。
5. **多源区间不一致时，写区间范围（如 8–40%）并注明出处，不写死单值**（v1 S8 的教训）。
