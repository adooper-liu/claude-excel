## 0. 批判结论（先行）

上轮拆解**方向对了一半**：settlement（结算单）确实是亚马逊卖家对账的锚点，
「钱去哪了」确实是老板第一问。但整体犯了三个错：

1. **信源标注不诚实**：13 条信源里 1 条**语义被改写**（S9 德勤 68%），2 条官方链接**从未开原文**
   （S1/S2），5+ 条是第三方聚合/营销博客转述却统一标「已确认」。
2. **原点判断过度演绎**：把「订单+广告」预设换成「结算单」预设，依然是**单平台（亚马逊 FBA）演绎**；
   且混淆了「现金实现」与「财务原点」——结算单是**结果**（实收），不是**原因**（决策依据）。
3. **场景未收敛 + 定位错置**：6 个场景实际只有 2 个独立；且把**技术门禁**（Gate 1b 的本职）
   误当成了**商业场景**来推——业财核算正面撞 ERP 拳头功能，没有赢面。

## 2. 逻辑批判：原点判断的过度演绎

**原主张**：「财务原点不是订单报表，也不是广告报表，而是平台结算单。」

**批判**：

1. **结算单是「现金实现」（实收），不是「原点」。** 一笔跨境销售在财务上有三个记账时点：
   - 订单 = **应收**（收入发生日，谁欠我钱）
   - 结算单 = **实收**（现金实现日，钱什么时候到我账上）
   - 广告 = **费用**（成本发生，营销消耗）
   「财务闭环」的正确定义是**三账本对齐 + 差异解释**（订单额 − 平台扣费 − 退款 = 实收），
   结算单是**验证器**（对账的锚），不是**唯一真相**。

2. **结算单是结果，不是原因。** 它只有金额，没有「这笔销售是不是广告带来的」「这个 SKU 要不要补货」
   的归因信息。老板的**决策问题**（场景 2 的本意：哪个 SKU 赚不赚钱）仍然要订单×广告×COGS 交叉，
   结算单只能**验证**交叉出来的数对不对。所以「订单+广告」不是被结算单取代，而是**被结算单验证**。

3. **范式不普适**（上轮自己批判「订单+广告」是研发预设，本轮发现自己犯了一样的错）：
   - Temu 全托管/半托管：卖家只收**供货价**，没有对 C 端结算单，「钱去哪了」问题不存在
   - Shopify 独立站：钱从 Stripe/PayPal 进来，对账对象是**支付服务商对账单 + 银行流水**
   - 结算单范式只对 **Amazon FBA 卖家**严格成立
   修正表述：**「结算单是亚马逊 FBA 卖家的财务锚点」**，不是「跨境电商业财原点」。

## 3. 需求纯度批判：六个场景收敛为三个

**原主张**：六个场景（结算拆解/净利/广告归因/现金流/退款/多币种），按老板付费意愿排序。

**批判**：

| 原场景 | 独立性检验 | 结论 |
|---|---|---|
| 1 结算拆解 | 独立 | 保留 → H2 |
| 2 单 SKU 净利 | 独立 | 保留 → H1 |
| 5 退款全成本 | **⊂ 场景 2 的一个减项** + 场景 1 的一个费用行 | 合并进 H1/H2，不独立成景 |
| 6 多币种 | **⊂ 场景 1 的多平台变形** | 合并进 H2 |
| 4 现金流预测 | 依赖**结算历史**，新用户无历史数据，短期不可得 | 砍掉（等有 3+ 期结算后再说） |
| 3 广告归因 | 数据已有（orders+ads feed），可独立 | 保留为**验证性场景**（已有 ±7 天 reconcile，补警示列即可） |

- **「按老板付费意愿排序」无实证**：没有访谈、没有付费测试，是臆断。承认并修正——
  排序依据改为「**决策频率 × 决策金额 × 现有工具缺口**」，且标注「待真实用户访谈验证」。

**收敛后的高纯度需求**：

- **H1 单 SKU 净利核算**（保留，重写卖点）：净利 = 订单×汇率 − COGS − 佣金 − FBA − 仓储 − 广告 − 退款。
  卖点**不是「算净利」**（Excel 透视+SUMIFS 也能凑合），而是**口径可调 + 假设驱动重算 + 审计留痕**。
- **H2 结算单拆解**（保留，降级定位）：销售→到账桥表。定位从「商业闭环」降为**技术验证 feed**，
  证明「CSV → 对账 → 审计」管道能接住平台结算单这种结构最复杂的数据源。
- **H3 敏感性/假设分析**（**新增主战场**）：退货率 8%→12%、汇率 7.2→7.0、佣金 15%→17%，
  净利怎么变？哪些 SKU 到临界点就亏？——**这是 ERP 给不了的（ERP 口径是死的）、Excel 天然主场、
  AI 增量最明显**（自然语言改假设 + 自动生成活公式 + 解释）。

## 4. 商业定位批判：技术门禁 ≠ 商业场景

**原主张**：Gate 1b 是「业财闭环」的商业场景，补上 settlement feed 就能商业化。

**批判**：

1. **业财对账/利润核算正是积加/领星/马帮的拳头功能**（slogan 就是「业财一体化」），
   且**数据源（订单/结算/库存）本来就在它们手里**，走平台 API 自动同步；
   Claude Excel 目前是「用户手动导 CSV」——**自动同步 vs 手动导出，正面打没有赢面**。
2. **Gate 1b 的本职是技术门禁**：验证写格单通道安全、reconcile 算子质量、_pack_audit 审计机制。
   这个价值是**内部研发验证**，不是**外部商业卖点**。把它当商业场景推，是**范畴错误**。
3. **修正定位**：Gate 1b = **「技术验证闭环」**（证明管道能力），商业验证**另立场景**——
   优先 H3（敏感性分析），因为它命中「ERP 不做/做不好 + Excel 天然主场 + AI 增量明显」三条件。

## 5. 卖点批判：什么是真差异化

**原主张**（上轮隐含）：「活调假设」（改 B2-B4 单元格 → SUMIFS 重算）是差异化。

**批判**：改参数 → 公式重算，是**原生 Excel 的基础能力**（引用单元格而已），不是卖点。
**真差异化三件套**（都是 ERP 黑盒和原生 Excel 给不了的）：

1. **口径透明**：每个数字怎么算出来的，AI 写成可读口径 + 引用单元格的活公式，不是藏在系统里
2. **异常把关**：匹配率 <90% 标红、退款负金额不静默加进汇总、跨格式归因虚增 8-40% 给警示
   ——「留痕」升级为「把关」
3. **审计留痕**：源表 hash、假设参数快照、_pack_audit 行——对完账能给人看「这数怎么来的」

## 7. 结论：修正后的高纯度需求（一句话）

> **Claude Excel 业财场景的护城河不是「做核算」，而是「在 Excel 里，用自然语言把任意口径的
> 业财分析做出来、说清楚、改得动、可复核」。**
>
> - H1 净利核算：口径可调 + 假设驱动 + 审计（差异化载体）
> - H2 结算拆解：技术验证 feed（证明管道接得住最复杂的数据源）
> - H3 敏感性分析：商业验证候选（ERP 给不了、Excel 主场、AI 增量明显）
> - Gate 1b 定位：**技术验证闭环**，不是商业闭环；商业验证另立场景
