## A. 决策与可靠性（reliability-critique / architecture-llm-first 里的）

这组是最劝退的，全是数学味儿的词，但内核很简单。

| 术语 | 人话 |
|---|---|
| **P(错)** | 出错的概率。就是「这事儿会不会搞砸」的可能性。 |
| **P(错)≈0** | 几乎不会出错。比如「提取某一列」这种操作，搞砸的可能性极低。 |
| **P(错)有地板** | 出错概率有下限——不可能降到零。AI 再聪明也会偶尔犯傻，这是本质，改不了。 |
| **代价** | 出错后的损失大小。改坏源表 = 代价高；多写一张新表 = 代价低。 |
| **代价≈0** | 万一错了也没啥损失。比如写新表，错了删掉重来就行。 |
| **期望损失** | 出错概率 × 出错损失。就是「这个操作要是搞砸了，总共会亏多少」的预估。 |
| **期望损失不等式** | 决策依据，一句话：**错得起的事简单处理，错不起的事重点防**。不是「架构美不美」，是「亏不亏得起」。 |
| **ground truth** | 标准答案 / 真相。拿结果跟它比，才知道对不对。在 Excel 场景里，真相在用户手里——只有用户知道他要的是什么。 |
| **fail-visible** | 出了错能看见。别静默失败——悄悄把数据改坏了，用户还以为没问题，那才是最可怕的。 |
| **A 类错误** | 值错误。比如该填 100 填了 1000。能被检查规则抓到（类型、范围约束）。 |
| **B 类错误** | 意图错误。AI 理解成了另一件事，但操作本身「合法」。比如你要对账订单，它给你做了透视——没报错，但不是你要的。这种结构防不住，只能让用户在执行前确认。 |
| **提交门** | 高代价操作执行前，先给人看一眼、确认了再执行。不是「AI 做完你来检查」，是「AI 先说要做啥，你点头才动手」。 |
| **审计门** | 批量/无人值守场景没法逐个确认，就事后审计。代价是发现问题会滞后。 |
| **歧义前置** | 执行前把「我理解你要的是 A 还是 B」显式摆出来让用户选，而不是闷头做完。专门对付 B 类意图错误。 |
| **确认衰减** | 提交门用多了人会麻木——第 10 次认真看，第 100 次闭眼点确认。所以确认要做得轻量（一个干净的 diff + 一个决策点），别让人疲劳。 |
| **分层裁判** | 按错得起/错不起分工：几乎不会错的操作用简单规则（正则）快速处理；容易错且代价高的操作交给 AI 理解 + 人确认。不是「全删正则」也不是「全靠 AI」，是按代价分。 |
| **可靠性的剧场** | 批判用语：给行为补丁披上架构外衣，看起来很严谨，实际没真正解决问题。比如靠写 prompt 让 AI「别犯错」——AI 该犯还是犯。 |

## B. 架构与写格（CLAUDE.md 里的核心概念）

| 术语 | 人话 |
|---|---|
| **写格单通道** | 只有一条路能改 Excel 格子：用户/Skill → 核心算子 → Office JS → Excel。其他任何路径（Skill 直接写、Python openpyxl、user.* 直接写）都被禁止。就像家里只有一根进水管，装了水表和阀门——别的口子全封死。 |
| **三层（A/B/C）** | A = 核心算力（通用工具，写格）；B = 核心数据（站点配置，不写格）；C = 用户扩展（Pack/Skill/知识，不写格）。行业逻辑只进 C，不进 A——核心不认识任何行业。 |
| **核心算子** | 通用工具，约 28 个。比如对账、整形、提取、计算、透视、写公式。像乐高积木的标准件，不管什么行业都能用。 |
| **Pack** | 可安装的场景包。把某个行业的整套作业流程（Skill + 知识 + 配置）打包，用户装了就有 `/跨境业财` 这样的命令。类似手机的应用商店——核心是操作系统，Pack 是 App。 |
| **Skill** | 一个可执行的工作流。只编排核心算子，自己不写格。比如「先对账、再写参数、再算利润、再透视」这一串步骤就是一个 Skill。 |
| **算子 vs 口令** | 算子 = 底层工具，该做厚、参数化（提取、去重、大小写都是参数）；口令 = 斜杠命令，该做薄，只是加速器（`/对账` 比「请帮我核对这两张表」快）。别为每句中文写一个专用函数。 |
| **recipe** | 取数的配方。描述「从哪个网站、怎么点、提哪张表、进 Excel 后列怎么映射」。类似菜谱——照着做就能把网页表格搬进 Excel。 |
| **connector** | 数据源适配器。同一个作业流程，换数据源（CSV 换成积加/领星 ERP）只换 connector，recipe 和算子不动。就像换水厂不改家里的管道。 |
| **feeds schema / canonical 列** | 统一列名约定。不管数据来自 Amazon 还是 Temu，进 Excel 后都叫同一套列名（canonical）。这样下游作业不用为每个平台单独写一套。 |
| **user.***  | 用户自定义的本地函数（P1 功能）。跑在后端子进程里，有隔离和信任门。装 Pack 时如果含 user.*，会提示「这包含本地代码，确认安装」。主 API key 不会传给这些函数。 |
| **信任门** | user.* 执行前的授权检查。能力声明变了（比如函数新增了联网能力）必须重新授权，不能偷偷升级。 |
| **HANDLED_TOOLS / ADDIN_HANDLERS** | 三方锁步：前端注册的工具名、前端处理函数、后端校验——三处必须对得上，缺一个后端启动就失败。防止「manifest 里写了工具但没人实现」的幽灵工具。 |
| **三方锁步** | 见上。三张清单必须严格一致，对不上就拒绝启动。 |
| **run_flow** | 预编排的流程执行器。LLM 选流程，流程内部按固定步骤跑（inspect→算子→新表），源表不覆盖。把容易出错的「让 AI 自由拼工具」换成「AI 只选流程，步骤固定」。 |
| **预编排** | 提前把步骤写死在 Skill 里，不让 AI 临场决定先做什么后做什么。AI 只负责选哪个流程，不负责编排步骤。 |
| **Office JS** | 微软的 Excel JavaScript API。所有格子操作（读、写、公式、格式、图表）都用它做，在加载项里跑，不经过模型。省 token + 可靠。 |
| **BYOK** | Bring Your Own Key。用户自己填 API key（DeepSeek/通义/GLM），不绑死任何一家，也不绑 Claude 付费账号。 |
| **:8765** | 后端端口，只绑 127.0.0.1（本机），不对外。LLM 代理、取数、知识库、user.* 都在这里跑。 |

## C. 业务概念（product-vision / pain-points 里的）

| 术语 | 人话 |
|---|---|
| **二段对账** | 跨境电商的利润要核对两次。第一段：订单 × 广告 → 毛利假设（我们做）；第二段：毛利 − 佣金 − 收单费 − 汇损 → 净到账（留给 Antom/连连做支付的那方）。我们在中间留了接缝，第二段接进来时作业流程不用改。 |
| **第一段** | 订单 × 广告 → 利润假设。把「卖了多少」和「广告花了多少」对上，算出每个 SKU 大概赚不赚。 |
| **第二段** | 利润 → 净到账。扣掉平台佣金、支付手续费、退款、汇率损失，算出真正到银行的钱。这层我们不做，留接口。 |
| **ERP = 上游水厂** | 店小秘/马帮/积加/领星这些 ERP 是数据供应商（水厂），不是竞争对手。它们把平台 raw 数据洗干净，我们拉同构表进来做它们不做的那层（本机假设/对账/透视）。 |
| **取数** | 把网页或 ERP 里的**表格**搬进 Excel。产出是一张 Excel 表。走取数栏、recipe、`/取数`。 |
| **调研** | 核实开放信息、对比口径、给摘要和引用。产出是对话里的结论，不进表。走 `/调研`、默认对话。跟取数是两码事，别混。 |
| **知识库** | 用户上传的文档（.md/.txt/.csv），本机做向量索引，对话时检索相关片段引用。不进表，不编造。跟取数、调研也是三码事。 |
| **Gate 1b** | Phase 1 的验收关卡：用 `/跨境业财` Pack 在 30 分钟内从脏数据跑通「订单×广告→利润假设」，源表不改，录屏可复现。通过了才进 Phase 2。 |
| **Phase 0/1/2/3** | 路线图阶段。Phase 0 = 底座造好；Phase 1 = 一个垂直场景跑通（Gate 1b）；Phase 2 = 接 ERP + Pack 订阅；Phase 3 = 第三方上架 Pack。Gate 驱动，不是日历驱动——达不到验收标准不进下一阶段。 |
| **ICP** | 理想客户画像。这个项目的：5-50 人跨境团队，Excel 当业财系统用，不想上全链路 ERP，不敢让 AI 碰源表，愿意自带 API key。 |
| **归因窗口** | 广告点击后多少天内的成交算这个广告的功劳。亚马逊 SP 广告 7 天，SB/SD 14 天。问题：广告按点击日记，订单按成交日记，直接汇总会对不上。我们只标注这个偏差，不强行解决。 |
| **ACOS** | 广告花费 ÷ 广告带来的销售额。花 100 块广告带来 500 块销售，ACOS = 20%。越低越好。 |
| **TACOS** | 广告花费 ÷ 总销售额（不只广告带来的）。比 ACOS 更能看出整体健康度。健康带 8%-15%，不是网上传的 25%-35%。 |
| **SOP** | Standard Operating Procedure，标准作业流程。Pack 本质就是可安装的 SOP。 |
| **SKU** | 商品编码，每个具体商品款的唯一标识。一个 ASIN 可能对应多个 SKU（不同颜色/尺寸）。 |

## D. 工程协作（AGENTS.md / coordination.md 里的）

| 术语 | 人话 |
|---|---|
| **二段协同** | Claude Code 出方案（只读，不写代码）→ Codex CLI 照方案执行（写代码）。中间用 git 桥交接。适合能写成完整方案、要自动跑的复杂任务。 |
| **串行化** | 同一时刻只有一个工具在 master 上改代码。不是「各干各的并行」，是「一个干完合并了，下一个再从最新 master 开工」。防止冲突。 |
| **任务 brief** | 一个任务的说明书，写在 `docs/tasks/<任务>.md`。有 frontmatter 状态（进行中/完成）、目标、边界、验收标准、进度 log。 |
| **worktree** | git 的工作树隔离。项目里有个只读分析 worktree（`d:\claude-excel.worktrees\project-issue-analysis`），只能看不能改。 |
| **manifest / executor** | 每个工具有两样东西：manifest（声明「我叫什么、做什么」）和 executor（实际执行函数）。缺 executor 后端启动就失败——不允许「有声明没实现」的幽灵工具。 |
| **typecheck** | TypeScript 类型检查。改完代码必须过，防止类型错误。 |
| **三方锁步** | 见 B 组。前端工具名 / 前端处理函数 / 后端校验三张清单必须一致。 |

## E. 沉淀规则 R1-R6（修错过程提炼的，architecture-llm-first 里）

| 编号 | 人话 |
|---|---|
| **R1** | 判断「做完了没」别靠 AI 说了什么，靠能检查的信号——版本号在不在、工具有没有被调用、键存不存在。措辞能有一万种说法，信号只有有或没有。 |
| **R2** | 生成的新表必须跟源表对账验证（匹配/冲突/左独有/右独有），全绿才算完成。别让 AI 自己说「我做对了」。 |
| **R3** | 稳定的知识学一次存下来，别每次从零推导。比如表结构——inspect 过一次就存笔记，下次直接用。 |
| **R4** | 修问题先找根：这类为什么会错？修通用规则，别写死单点。给单个 case 打补丁 = 没找到根。 |
| **R5** | 按错得起/错不起分工（见 A 组的「分层裁判」）。 |
| **R6** | 任何任务都按「读懂表 → 定方案 → 选工具 → 验证」的顺序走。跳过「读懂」直接套公式 = 蒙列名。 |
